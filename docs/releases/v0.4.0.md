# VeriRun v0.4.0 — Durable Control Plane

v0.4.0 delivers M3's durable control-plane contract: evaluation runs can be
created, inspected, cancelled, resumed, and replayed without silently changing the
verification policy or accepting duplicate authoritative results.

## Included

- A deterministic, versioned `VerificationPlan` compiler and lifecycle. Only a
  validated and frozen plan can be scheduled.
- PostgreSQL-backed plan, cohort, run, task, lease, final-result, command-receipt,
  and artifact-metadata state with explicit legal transitions.
- Lease claim, heartbeat, expiry, reclaim, worker takeover, and late-result
  rejection semantics.
- Caller idempotency keys and one authoritative final result for each
  `run + task + candidate + verification-plan digest` identity.
- Cohort preflight and automatic splitting when a plan, verifier image, required
  evidence policy, or aggregation policy changes.
- SHA-256-addressed S3-compatible artifact storage and typed `verirun control`
  lifecycle commands.
- Public JSON Schemas, a lifecycle ADR, recovery documentation, and PostgreSQL +
  MinIO integration tests in CI.

## Evidence

The release assets contain the final [control-plane recovery report](../../evidence/v0.4/control-plane/REPORT.md)
and its machine-readable `summary.json`. The smoke records the exact source state,
PostgreSQL and client versions, MinIO server identity, migration version, plan
digests, artifact digest, failure domains, and eleven acceptance checks.

The evidence exercises control-plane client reconstruction, expired-lease reclaim,
worker takeover under the same frozen plan, late-result rejection, exact duplicate
commit, changed-plan cohort splitting, mixed-aggregation rejection, and a live
S3-compatible artifact round trip. The release CI repeats the PostgreSQL and MinIO
recovery smoke on Linux after lint, typing, Schema, test, build, and earlier replay
gates pass.

## Delivery semantics

- Task attempts are at least once. A worker may execute again after a lease expires.
- The PostgreSQL commit boundary is effectively once for the authoritative final
  result. It does not make execution itself exactly once.
- Every durable task, lease, and final result retains the same verification-plan ID
  and digest selected before candidate execution.
- Candidate contents, model identity, and already-produced output are not inputs to
  verification-plan selection.

## Supported boundary

The published recovery claim is limited to the recorded local, single-node
PostgreSQL 16.13 and MinIO environment plus the corresponding GitHub Linux CI
fixture. The S3-compatible adapter has MinIO evidence only.

## Known limitations

- This release is not a production-readiness, high-availability, or disaster-
  recovery certification.
- PostgreSQL failover, multi-node concurrency scale, object-store outage tolerance,
  backup/restore operations, and long-duration soak behavior are not evidenced.
- Multi-tenant authentication/authorization, result signing, and artifact retention
  policy are not implemented.
- Exactly-once execution is not claimed; only the authoritative result commit is
  protected against duplicate or changed repeated payloads.
- LLM-routed planning, case-specific dynamic verifier selection, multi-agent verifier
  orchestration, dashboards, Kafka, Temporal, Ray, and KubeRay are outside v0.4.

## Upgrade notes

The public Python package version changes from `0.3.0` to `0.4.0`. Existing v0.1-v0.3
protocol, gateway, and isolated-execution paths remain available.

Install the control-plane dependencies separately, then initialize or upgrade the
database:

```bash
python -m pip install -e '.[control-plane]'
verirun control --dsn "$VERIRUN_POSTGRES_DSN" migrate
```

The database migrator is idempotent and advances the M3 schema to migration version
2. Legacy v1 task-attempt and verification-result records may carry an optional
paired verification-plan ID and digest; the durable v0.4 path always records plan
lineage directly on its task, lease, and final-result records.
